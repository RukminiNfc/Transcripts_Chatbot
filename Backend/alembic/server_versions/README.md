# Server-chain migrations

Migrations for **production only**. They are kept out of `alembic/versions/` deliberately.

## Why this folder exists

Local and production have had different Alembic histories since 2026-06-23:

```
production :  ff33b853ad6c          ("create all tables" — one autogenerated snapshot)
local      :  671ce19ff326 -> 581dc104a85c -> 35c88d91e71e -> d1f499637722
                                                 -> a7c3e1b9d204 -> b4f82a6c1e37
```

Neither chain contains the other's revisions. Production's schema has also been extended
outside Alembic — `users` and `meeting_minutes` were both created by `create_all`, not by any
migration — so Alembic has never been the full source of truth there.

The practical consequence: a migration written against the local chain does nothing on
production, because its `down_revision` does not exist there.

## Why not just put them in alembic/versions/

Alembic loads every file in that directory and resolves one graph. A file whose
`down_revision` is missing raises `KeyError` on **every** Alembic command, including
`alembic current`. Keeping these here means local Alembic keeps working.

## Rules

- **Production:** copy the file into `alembic/versions/`, then `alembic upgrade head`.
- **Local:** never copy these in. The equivalent change is already in `alembic/versions/`.
- Never let both versions of the same change sit in one `alembic/versions/` directory —
  Alembic then sees two unconnected roots and every `upgrade head` fails with
  "Multiple head revisions are present".

## Worth fixing properly at some point

Two chains for one schema means every future column needs writing twice. The real fix is to
collapse both sides onto one baseline that matches production and stamp both environments to
it. That is a deliberate piece of work, not something to attempt during a deployment.
