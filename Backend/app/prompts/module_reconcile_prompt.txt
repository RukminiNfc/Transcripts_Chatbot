WHAT TO DO WITH EACH NEW REQUIREMENT

1. MODIFY — it describes the same rule as an existing bullet, with different detail.
   Rewrite that bullet in place. Do not add a second bullet alongside it.
   Examples of the same rule changing: a count or threshold moves (three options becomes four),
   a mechanism changes (manual becomes automatic), scope widens (temp orders becomes temp and
   permanent orders), a value is corrected.

2. ADD — it is a genuinely different rule.
   Append it under the most fitting existing "### " sub-heading, or create a new sub-heading
   when none fits.

3. DEPRECATE — the client explicitly cancelled or replaced an existing rule.
   Prefix that bullet with "~~DEPRECATED~~ " and leave the text intact. Never delete it: a
   requirement that was withdrawn is part of the history, and a reader needs to see that it was
   considered and dropped rather than wonder whether it was ever discussed.

4. SKIP — it restates an existing bullet with no new information.
   Leave the document unchanged for that one. Re-stating a rule is not a change.

JUDGING "SAME RULE" vs "DIFFERENT RULE"

This is the decision the whole document depends on. Two statements are the SAME rule when they
govern the same subject AND the same aspect of it — so the new one is an updated version of the
old. They are DIFFERENT rules when they could both be true at once, even within one feature.

  SAME      "Add a third selectable option" / "Add a fourth selectable option"
  SAME      "Rollback is manual" / "Rollback runs automatically via Azure DevOps"
  DIFFERENT "Allow selecting the target environment" / "Use dropdown values for parameters"
            (WHAT you select versus HOW you select it)
  DIFFERENT "API and UI deploy separately" / "UI deploys only its configured folder"
            (deploy ordering versus deploy scope)

When a new requirement would modify an existing bullet, prefer MODIFY over ADD. Adding a near
duplicate is the failure this document exists to prevent — a rule discussed in five meetings
should be one bullet with five revisions behind it, not five bullets.

WRITING THE DOCUMENT

- Keep the existing structure. Reuse "### " sub-headings rather than inventing variants of them.
- Each bullet is one complete, imperative sentence a developer could implement without reading
  the transcript.
- Preserve exact table names, column names, status values, thresholds and numeric values.
- Do not summarise or merge unrelated bullets. Length is not a problem; losing a requirement is.

OUTPUT

Return ONLY the "### " sub-sections you are changing. Sub-sections you do not return are kept
exactly as they are — you do not need to repeat them, and you must not return a sub-section you
did not change merely to restate it.

Respond with ONLY JSON in this exact shape:

{
  "revision_summary": "one sentence naming what changed in this revision",
  "sections": [
    {"heading": "Applicant Source", "action": "REPLACE", "content": "- first bullet\n- second bullet"},
    {"heading": "ICU Resume Queue", "action": "NEW",     "content": "- first bullet"}
  ],
  "diffs": [
    {"action": "MODIFIED",   "sub_heading": "...", "old_text": "the exact bullet text being replaced", "new_text": "the new bullet text"},
    {"action": "ADDED",      "sub_heading": "...", "new_text": "the new bullet text"},
    {"action": "DEPRECATED", "sub_heading": "...", "old_text": "the exact bullet text being deprecated"}
  ]
}

RULES FOR "sections"

- "heading" is the sub-heading text WITHOUT the leading "### ". For a REPLACE it must match an
  existing sub-heading EXACTLY as written in the current document — it is used to find the
  sub-section being replaced, so an approximation creates a duplicate sub-section instead.
- "action" is "REPLACE" for an existing sub-section, "NEW" for one that does not exist yet.
- "content" is the COMPLETE body of that sub-section: every bullet it should contain afterwards,
  including the bullets you did not touch. Anything you leave out of "content" is deleted from
  that sub-section. Do not include the "### " heading line inside "content".
- A sub-section you changed must appear exactly once in "sections".

`old_text` in "diffs" must be the bullet's text EXACTLY as it appears in the current document,
without the leading "- ". It is matched against the document to locate the requirement being
changed, so an approximation silently fails to match.

Report only real changes. A module where everything was SKIPped produces an empty "sections"
array AND an empty "diffs" array, and that is a correct and expected outcome — not every meeting
changes every module.
